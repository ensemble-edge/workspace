# Brand Colors — strategy & implementation spec

The Brand Colors tab is being redesigned around a single principle: be prescriptive enough that any operator ends up with a world-class palette, while remaining flexible enough that an experienced designer never feels boxed in. The structure has four primary tiers — Brand palettes, Neutral, Gradients, and Themes — plus a separate Semantic colors block for state indicators. Operators commit to four to six anchor hex values total across the entire system; everything else derives algorithmically. The current implementation sprawls because it generates 10-rung Tailwind-style ladders for every color including backgrounds, treats light and dark as background hexes rather than themes, and exposes too many independent surfaces to the operator. The redesign collapses that into a tight, role-named, theme-aware model.

Brand palettes (Primary, Secondary, Accent — hard-capped at three) are the operator's main direct color input. Each palette has a required editable name like "Ownly Coral" or "Lagoon," and one operator-typed Main hex; the system derives four sibling tiers — Dark, Bright, Pastel, Faded — in OkLCh space at fixed perceptual offsets from the Main, so every palette renders as a five-rung horizontal strip rather than a 10-step ladder. Role names (not numeric shades) are the canonical reference in consumer code: `primary-bright`, `accent-faded`, `secondary-dark`. This means renaming a palette doesn't break anything downstream, since the role is the stable contract. Individual rungs can be overridden by the operator, but the override affordance lives behind an "inspect" disclosure on each row, not in the default view.

Neutral is a single palette with the same five-rung structure, derived by default from Primary (producing a branded gray) with a hue selector offering Branded / Warm / Cool / True alternatives. Neutral drives all surfaces, borders, and muted text — this replaces the current pattern where background-light and background-dark each get their own ladder. There is no longer a separate "background palette"; backgrounds are roles that resolve to neutral rungs.

The Gradient builder is intentionally token-only: stops are picked from existing palette rungs (Primary · Bright, Accent · Main, etc.) rather than arbitrary hex, plus two always-available system tokens — `white` and `black` — for hero-style fades and high-contrast bookends. Each gradient has a required editable name, two-to-four stops, a preset angle (0° / 45° / 90° / 135° / 180°) or Radial mode, and emits a CSS variable like `--gradient-sunrise` for consumption. Hex inputs are deliberately not allowed in the gradient builder: if a stop isn't in any palette, the operator should override a palette rung first or add a new palette, which preserves the cascade contract — touch primary, every gradient referencing it updates. Hard-cap named gradients at five; anything beyond belongs in component code, not the brand system.

Themes (Light, Dark) are parallel first-class concepts, each binding semantic roles — canvas, surface, text-primary, text-muted, brand, brand-bg, border — to palette rungs or hex values. Dark theme is optional; a workspace with no dark theme configured can still ship, but the Logo Builder won't generate dark-background lockups and the variants matrix shows an "Add a dark theme" placeholder where dark-bg rows would render. The minimum bar for "dark theme configured" is one field: the dark canvas hex. Everything else auto-derives from there and is tunable later. This gates the existing logo-builder dark-bg lockups behind the existence of a dark theme rather than reading a top-level `background-dark` hex.

The "Generate from light" action on the dark theme card is pure deterministic color math, not AI. It performs three transformations. First, canvas inversion via OkLCh: flip the canvas L around the midpoint with a bias toward a dark plateau (target L ≈ 0.14), preserve hue exactly, reduce chroma to roughly 0.7× to avoid muddy warm darks; surface lifts +0.05 L from canvas. Second, brand binding via contrast preservation: for each role bound in the light theme, compute its APCA contrast (preferred over WCAG 2.x; fallback acceptable) against the light canvas, then pick the rung from the same palette whose contrast against the dark canvas is closest to that target. So if `primary-main` gives 4.8:1 on the light canvas, the dark theme picks whichever rung in the primary palette lands closest to 4.8:1 on dark — usually `primary-bright`. This is why the rung-lift-on-dark heuristic isn't hardcoded; it falls out of the math. If no rung in a palette lands within ~10% of the target contrast, that binding gets a warning icon rather than a silent bad pick — the operator can override manually or adjust the underlying palette. Third, foreground text: APCA max-contrast pick against the canvas, biased slightly toward the canvas hue so the foreground doesn't feel sterile (text on a warm dark canvas picks up a hint of warmth rather than going pure `#FAFAFA`). Use the `culori` library (MIT, OkLCh + Oklab + WCAG + APCA all built in, around 30KB tree-shakeable). Total implementation is roughly 80 lines of color math; the work is mostly orchestration. Generation is deterministic — same inputs always produce the same outputs, fully auditable, no API calls, no latency.

The Logo Builder's existing `background-light` and `background-dark` configuration migrates to read from theme tokens rather than two separate top-level hex fields. The Logo Builder's background picker presents two input modes via the same popover modal pattern used elsewhere: pick from theme tokens (`light.canvas`, `dark.canvas`, `light.brand-bg`, `dark.surface`, etc.) via a dropdown of available theme tokens, OR enter an arbitrary hex via the color picker. This is the one place in the entire brand system where arbitrary hex is permitted, and the reasoning is deliberate: logos legitimately get placed in unpredictable contexts — partner co-marketing pieces, PMS-matched physical merch, third-party platforms, conference backdrops — and forcing those into the brand token system would create palette pollution worse than allowing freeform hex at the asset-rendering layer. Logos rendered against light-theme backgrounds use the light foreground bindings; logos against dark-theme backgrounds use dark foreground bindings; logos against an arbitrary hex run the same APCA contrast check at render time to auto-pick the foreground color and ban contrast-failing finish×background pairs in the variants matrix as today.

Semantic colors (Success, Info, Warning, Error) remain a separate, independent system — each is a Main + Light hex pair, picked directly without palette derivation. These are deliberately not part of the brand palette structure: state indicators serve a different role and shouldn't shift when brand identity changes. Keep the existing semantic colors implementation; do not consolidate it into the brand palette model.

## Implementation requirements

Use existing Ensemble UI components throughout — Input, Select, Button, Card, Modal, Popover, Tabs, Tooltip, and any existing color-picker primitive — rather than building new component primitives. This redesign is structural and stylistic, not a new component library; if a control doesn't exist in Ensemble UI yet, prefer composing from existing primitives over adding new ones, and flag any gap rather than inventing a one-off.

All color and hex pickers must be popovers or modals — click a hex value or swatch and a popover opens with the picker UI. Never use inline color picker widgets that take up row space; the entire compactness goal of this redesign depends on the swatches being readouts that open pickers on click, not always-expanded controls. Color picker popovers should support direct hex input, HSL/RGB sliders, the browser `EyeDropper API` where the platform supports it, and a "recently used" strip drawn from the workspace's existing palette tokens so operators don't accidentally introduce drift.

Token references in code remain role-based (`primary-bright`, `neutral-faded`, `gradient-sunrise`) so palette renames cascade cleanly with no consumer-code changes. Every operator change emits `brand.tokens.changed` as today, which the variants matrix, favicon suite, `/brand` public guide, the brand CSS endpoint (ETag-revalidated), and every downstream consumer subscribe to. The brand CSS endpoint emits CSS custom properties at the same `/brand.css` URL with the same shape, just expanded — `--primary-dark`, `--primary-main`, `--primary-bright`, `--primary-pastel`, `--primary-faded`, plus the gradient and theme variables.

The reference HTML mockup provided alongside this spec shows the intended layout: editable palette names, five-rung horizontal strips, compact gradient rows with token-only stop chains, side-by-side light/dark theme cards with a "Generate from light" action, and a four-up semantic colors grid. Match the structural pattern, not necessarily the literal styling — apply Ensemble UI tokens for typography, spacing, and borders rather than the hand-rolled CSS variables in the mockup.
